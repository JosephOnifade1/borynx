# Phase 3 — Verified email intake (staging runbook)

**Off by default.** This phase supplies a Supabase Auth adapter and a disposable rehearsal. It does not choose a hosted project, configure a sender, send real mail, or open public intake. PostgreSQL and Drizzle remain the only app data layer.

## Guest and reviewer walkthrough

1. In the staged app, open `/l/new` as a guest. Fill the usual brief, budget and skills. **Continue to email** opens the contact step: email and name are required, company is optional. The app creates a private draft only; nothing is in the lead board or the moderation queue yet. The tab may keep the brief locally, but does not store contact details there.
2. Open the latest link in the same browser profile where it was requested. Use a normal top-level tab, not a mail app's separate webview or an embedded preview. The link is short-lived (configure 15 minutes at the provider). A resend can replace the prior link; it neither replaces an already stored brief nor extends the draft's expiry. The app holds one active link request per browser. If the link is stale or an email scanner used it first, request a new one after the cooldown.
3. The link signs you in and returns to the **exact** saved brief. Check the details and press **Submit for review**. Only that action creates an owned, pending lead. A separate `/login` email sign-in, even to the same address, cannot confirm a saved brief without its original intake context. If the brief expires or its deadline/space is no longer valid, start a new brief.
4. The owner can open the pending submission. Only a separate authorized site reviewer can approve it in `/mod/queue` (or ask for edits/reject it). All first-time, returning, and flagged submissions stay pending until explicitly published. An email sign-in is not a verified client badge, GitHub verification, escrow, or payment proof. Pitch privacy and award/completion rules are unchanged.

## Rehearse without a provider or outbound mail

Use Node 22, npm 10, `openssl`, and a supported embedded PostgreSQL platform. Stop any Next dev process in this checkout, then run:

```sh
npm ci
npm run test:db -- --email-only   # Phase 2 → Phase 3 upgrade and staged HTTP flows
npm run test:db                   # also exercises all prior upgrades, local demo, and marketplace flows
```

The runner uses a private loopback PostgreSQL and a temporary HTTPS provider double. It checks exact redirect/PKCE exchange, real database transactions, sign-in/replay/expiry, wrong context, legacy account isolation, private grants, concurrency, delivery failures and send limits. The double has no real inbox or sender. Passing this does not establish that a real Supabase project, SMTP sender, or email client works.

## Before enabling on hosted staging

- **Approve the targets first.** Choose a dedicated Supabase Auth project, the exact staging HTTPS origin, an isolated app PostgreSQL database, and the sender and internal test inboxes. Do not repurpose a project's existing users or assume a connected project is staging. Back up any staging data, rehearse on a copy, and apply the checked-in journal (`npm run db:migrate`) before accepting writes. Migration `0008` is additive and does not link any legacy user or activate any legacy session.
- **Keep the database private.** Separate app PostgreSQL from the auth project, use a direct app-only connection, and keep Borynx tables out of the Data API/GraphQL and any public database grants. Use a server-owned Borynx schema role; do not grant browser roles database credentials. Stage startup rejects `PUBLIC` and direct/inherited `anon` / `authenticated` application table grants, including relevant column grants. Check other roles and network exposure separately; this check is not a substitute for keeping the Data API off. The private auth schema and the session table have RLS with no browser policies. Use an empty staging database or test-only data. Revoke any copied sandbox sessions before allowing external access.
- **Configure Supabase Auth** for email confirmation with email signup enabled, no anonymous sign-in or other providers, and a suitable test SMTP sender. Set the Site URL to the approved staging host; only allow the exact `https://<staging-host>/api/auth/callback` redirect (no wildcards). Use the managed `{{ .ConfirmationURL }}` in **Confirm signup** and **Magic Link** templates, set the expiry to 900 seconds, leave confirmation enabled, and disable click-tracking/rewriting. Keep provider-side send limits and a staging recipient allowlist at the mail/provider boundary. Do not put a service-role key in Borynx or expose the publishable key via `NEXT_PUBLIC_*`.
- **Configure trusted HTTPS ingress.** Forward the canonical public `Host` to Next. Strip any caller-provided `X-Borynx-Client-Ip` and replace it with one validated client IP from your trusted edge; do not just take the caller's `X-Forwarded-For`. The app listener must be reachable only through that trusted ingress. Verify this from outside before enabling sends. Use the production build (`next start` or your hosting equivalent) and first-party top-level HTTPS, not an iframe. Don't log callback query strings, request bodies, cookies or provider responses in edge logs, tracing, or monitoring; the standard Supabase redirect attaches a single-use, PKCE-bound exchange code, not an email, access token, or brief. The app immediately redirects away from that URL with no-referrer/no-store headers.
- **Set server environment** (see `.env.example`). `BORYNX_EMAIL_AUTH=staging` plus `BORYNX_AUTH_ORIGIN` and `BORYNX_SUPABASE_URL` as HTTPS origins (no trailing slash), `BORYNX_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…`), explicit `DATABASE_URL`, and `BORYNX_EMAIL_AUTH_SECRET`. Generate the last value on a trusted system using `node -e 'process.stdout.write(require("node:crypto").randomBytes(32).toString("base64url")+"\n")'`; put it in the hosting secret store, not Git or chat. Keep it identical across app replicas. Both demo flags should be `0`. Initially leave `BORYNX_EMAIL_SENDS=0`; use `1` only for approved staging inbox tests.
- **Schedule retention** with the staging DB role: run `npm run db:prune-email` at least every 5 minutes and monitor failures. An unclaimed brief becomes unreadable and unconfirmable at 24 hours; the next run scrubs the brief and contact details. Confirmation scrubs them immediately. An opaque receipt with keyed fingerprints remains for up to a further 24 hours to detect expiry/retries, then is deleted (older references return `404`). Send reservations are pruned after 24 hours. Keep backup retention aligned with the same privacy expectations.
- **Review with internal inboxes first.** Test first-time signup, return sign-in, both signup and magic-link templates, scanned/used/expired mail and resend, abandoned intake, real first-party cookies and sign-out. Test that account switching cannot show another draft and that only an explicit reviewer can publish. Provision test reviewer roles only after verifying the intended staged identity; do not match existing staff by handle or email. Check a narrow screen and keyboard use. Passing staging is not approval for an outside pilot.

## Operational details

- New intakes: two per rolling hour per trusted ingress IP. Outbound attempts across regular sign-in and intake: a 60-second address cooldown, at most three per address/hour, six per ingress IP/hour, and 30 app-wide/hour. Limits use HMAC-based fingerprints and persist before contacting the provider, even on failure or concurrent retries. A lost response can be retried without creating a duplicate draft. Rotate the HMAC secret only as a planned change: outstanding flow cookies and intake fingerprints will no longer match.
- `POST /api/leads/intake` and `POST /api/auth/email` return a generic `202 { "status": "check_email" }` without account or draft information. `GET /api/auth/callback` only authenticates and redirects. `POST /api/leads/intake/confirm` requires a valid first-party session and matching opaque draft context. It returns `201` for a new pending lead or `200` for its same-actor retry, with `404` for a wrong account/context and `410` for an owned expired draft still within retention. An unauthenticated request is `401`.
- App accounts map only from the confirmed Supabase project/subject pair. Existing profiles are never overwritten by intake contact details. Email lives in the private identity table and not in public user responses. New profiles may use the supplied name; company is retained privately. Verified sessions are app-owned, hashed in PostgreSQL, cookie-only, and time out after seven days. Logout revokes that session. If a provider account must be disabled immediately, revoke its app sessions too; the app does not store provider tokens or continuously poll Auth.
- To pause delivery, set `BORYNX_EMAIL_SENDS=0` and redeploy/restart. Already issued sessions can continue; links can still finish sign-in until expiry. To disable managed sign-in/session acceptance entirely, turn off `BORYNX_EMAIL_AUTH`. Never turn on demo credentials to work around a provider failure.
